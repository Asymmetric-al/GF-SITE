## 3. Core Payload CMS v4 Delivery Boundary

- **Strict separation:** `GF-SITE` consumes `Asymmetric-al/core` strictly through server-only HTTP reads (`src/lib/content/`) with zero Payload or database runtime dependencies (`docs/core-integration.md`).
- **Immediate withdrawal and redaction posture:** Revocable public endpoints (`project-pages`, `navigation`, `updates`, `missionary-pages`) run uncached (`cache: "no-store"`) with React per-request deduplication; `/projects` and `/missionaries` verify linked entries in bounded batches directly against Core so uncoordinated withdrawal removes titles immediately without single-document failures collapsing the whole list.
- **Pre-stream serving admission, true no-JS semantic `<main>`, Core UUID payment contract, and runtime CSP:** `src/proxy.ts` validates `/projects/:slug` and `/missionaries/:id` locally before calling Core, emits the single authoritative runtime `Content-Security-Policy` header (`src/lib/http/csp.ts`) permitting runtime `CMS_BASE_URL` / `CMS_MEDIA_ORIGIN` media and configured `DONOR_APP_BASE_URL` `form-action` origins across `/projects*` and `/missionaries*`, passes standalone standing routes straight to statically prerendered directories and `generateStaticParams()` detail pages (so `<h1>` and `<form>` render strictly inside `<main id="main-content">` before `<footer>` even with JavaScript disabled), internally rewrites Core-connected requests to identity-free `/projects/live`, `/projects/live/:slug`, `/missionaries/live`, and `/missionaries/live/:id` with scoped single-use short-TTL tokens plus stateless HMAC-SHA256 multi-instance serverless fallback (`src/lib/content/admission-handoff.ts`), returns genuine HTTP `404` on missing or withdrawn entries, and returns genuine HTTP `503` (`Retry-After: 60`) on Core outages via accessible standalone Brand-Kit HTML (`src/lib/http/standalone-notice-html.ts` with vendored `Source Serif 4` and `Nunito`). Online checkout plumbing (`/checkout`, `/give/checkout`, `/donor-dashboard/*`, `/login`) enforces one authoritative server-side recipient state machine (`classifyCheckoutDesignation()` + `resolveAuthoritativeCheckoutRequest()`): General Fund aliases (`general`, `general-fund`, or genuinely unspecified requests) map cleanly to `fund=general` (`The Global Fellowship General Fund`), UUID-formatted IDs (and optional `CORE_DONATION_ID_MAP` env UUID mappings) route into Core's Donor Application (`DONOR_APP_BASE_URL`, one-time online checkout contract requiring donor sign-in; monthly requests stay cleanly on `/give/checkout` with an opaque UUID `Designation reference` in Finance inquiries and a separate explicit `frequency=one-time` option) only when any paired `workerId` + `missionary_id` matches identically or via `CORE_DONATION_ID_MAP`, unmapped standing slugs (including `where-most-needed` until Finance maps its dedicated Core UUID) route synchronously to `/give/checkout` keeping `"Email Finance"` primary before any alternate General Fund option, and unverified `workerId`+UUID pairs, blank, malformed, conflicting, or unknown standalone slugs normalize to `designation_status=unresolved` across redirects, HTTP `400` amount-correction retries (with skip link and flex footer), and cadence switches so donor intent is never silently routed to the General Fund or displayed under an unverified profile name. `isOnlineCheckoutEligible()` requires both a configured `DONOR_APP_BASE_URL` and an eligible target before showing online checkout status copy or routing directly to Core checkout (while directory cards and detail widgets keep concise `"Give"` / `"Give $100"` action labels). All paths preserve raw invalid client input for accessible `role="alert"` errors under one exact-cent `$1.00` to `$1,000,000.00` validator (`parseGivingAmount`, accepting comma-grouped thousands), use same-origin HTTP `200` meta-refresh handoff on native `via=form` submits so Chromium and WebKit `form-action 'self'` never block JS-disabled giving, and contain zero Every.org fallback.
